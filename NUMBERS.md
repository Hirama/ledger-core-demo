# Numerical choices

Amounts are integer minor units throughout the core. The table separates numbers required by the request from numerical conventions selected for this implementation. “Why not half?” addresses the economic or structural effect of changing each choice; it is not a suggestion to tune money constants.

## Required economic numbers

| Number | Source and meaning | Why this value, and not half? |
| --- | --- | --- |
| 6 days, numbered 1 through 6 | Supplied replay and capitalization window | A three-day window omits required events and capitalizes before the specified end. |
| 2 accounts | Supplied ACC-001 and ACC-002 | One account removes the currency-precision and instalment problem. Account identifier digits are labels, not mathematical parameters. |
| AED scale 2 / factor 100 | Supplied currency precision; one minor unit is AED 0.01 | One decimal place would collapse distinct fils; halving 100 gives a unit of AED 0.02 and changes the currency's requested granularity. |
| BHD scale 3 / factor 1,000 | Supplied currency precision; one minor unit is BHD 0.001 | A scale of 1.5 is not a decimal precision. Halving 1,000 gives BHD 0.002 granularity and cannot represent the required smallest unit. |
| Opening balances 0 / 0.00 AED / 0.000 BHD | Supplied account openings | Half of zero is zero; a positive opening would change authorization and fee outcomes. |
| Daily interest 0.04% = 0.0004 = exact `1/2500` | Supplied economic rate | Half is 0.02%, an unauthorized change in interest. The rational form computes the given rate exactly. |
| AED fee 25.00 = 2,500 minor units | Supplied daily fee for ACC-001 | AED 12.50 would contradict the specified assessment. It is not a configurable optimization choice in this replay. |
| Zero BHD fee configuration field | No BHD fee or conversion rate supplied | Go's zero value means missing configuration, not a zero-fee exemption or a guessed half-sized fee. A negative BHD close emits a policy error. Half of zero remains zero. |
| Once per account per value day | Supplied fee frequency | Half an assessment is not a coherent journal event and would halve the authorized fee. The record itself prevents a second assessment. |
| Authorization floor 0 minor units | Supplied nonnegative-available-balance rule | Half is still zero. Allowing a negative floor would extend credit; requiring a positive floor would wrongly reject zero remaining availability. |
| Positive-interest floor 0 minor units | Supplied positive balances only | Half is still zero. Interest is zero on zero or negative balances; a positive balance may nevertheless round to zero interest. |
| 3 instalments for E10 | Supplied split count | A fractional count of 1.5 cannot describe postings; reducing to one or two postings changes the requested stream. |

The supplied event magnitudes are not chosen constants: AED 1,200.00 / 120,000 minor units; 950.00 / 95,000; Auth-A 200.00 / 20,000; 400.00 / 40,000; settlement 185.00 / 18,500; unknown settlement 180.00 / 18,000; late debit 620.00 / 62,000; Auth-B 90.00 / 9,000; and BHD 10.000 / 10,000. E9's 62,000-minor-unit compensation is derived from E7, not accepted as a caller-supplied magnitude. Halving any supplied magnitude changes the scenario rather than exercising it.

The supplied booking/value days are also fixed inputs: E1 `(1,1)`, E2 `(1,1)`, E3 `(2,2)`, E4 `(3,3)`, E5 `(4,4)`, E6 `(4,4)`, E7 `(5,2)`, E8 `(5,5)`, E9 `(6,2)`, and E10 `(5,5)`. Event identifier digits and authorization letters identify commands; they are not configuration quantities. Their exact order has ten receipt attempts.

## Selected representations and algorithmic numbers

| Choice | Reason | Why not half? |
| --- | --- | --- |
| Signed 64-bit integer minor units; no fractional stored unit | Exact stored addition and comparison with checked bounds; `math/big.Int` and `math/big.Rat` preserve exact intermediate calculations | Half a minor unit violates the storage precision. Halving the width to 32 bits sharply reduces representable balances and aggregates; 64 bits is a Go standard integer width with practical headroom for this model. |
| Range `-2^63` through `2^63-1` minor units | Bounds inherent in signed `int64`; amount parsing, affected daily balances, available subtraction, and derived cash use checked conversion rather than wrapping | Halving these limits would invent a separate business cap. Halving the bit width would produce the much smaller signed 32-bit range. Production account limits should be explicit additional controls. |
| Base 10 exponentiation for currency scale | Decimal amounts and decimal places are required | Base 5 would encode a different numerical system and fail the currency precision. |
| Ties-to-even rounding | Midpoint behavior was unspecified; a deterministic convention avoids systematically rounding every tie upwards | “Half the rounding mode” is undefined. Half-up is a different policy, covered explicitly by midpoint tests. |
| Twice the exact rounding remainder; parity bit 0 | Comparing `2*remainder` with the denominator distinguishes below-half, exact-half, and above-half cases. At a tie, least-significant bit 0 identifies even and bit 1 odd | Halving the multiplier to 1 compares against a whole unit instead of half a unit and prevents correct nearest rounding. The bit position is the ordinary definition of integer parity. |
| Daily rounding once per final daily target | Makes every payable daily amount representable before it contributes to capitalization | Half a rounding operation is undefined; rounding only some days loses the exact sum guarantee. |
| Zero-accrual journal entries | A closed day has an explicit original accrual record, even if no interest is payable | Dropping half the zero records would make audit coverage dependent on day selection. This is an audit convention, not a monetary change. |
| Default zero amount on nonmonetary records and zero sum for empty projections | Receipts, errors, closures, cancellations, and expiry do not themselves move cash; zero is the additive identity | Half of zero is zero. A nonzero default would create an unintended monetary amount or corrupt empty-account queries. |
| Journal sequences start at 1 and advance by 1 | One-based cutoffs are easy to read; every receipt, error, posting, close, and adjustment has a distinct order | A half-step requires fractional sequence IDs with no benefit. Starting at zero is a viable alternative, but the implementation consistently uses one-based sequence numbers. |
| Query cutoff 0 means all current records; accrual day 0 means all days; end sequence 0 means not ended | Actual sequences and value days start at 1, so zero is an unambiguous optional-filter/status sentinel | Half of zero is zero. A positive sentinel would collide with a real record or day. |
| Observed day starts at 1 and advances one whole day at a time | Enumerates all required daily closes before later commands | Half-day steps would introduce an intraday calendar outside the request. |
| Instalment labels start at 1 | Human-facing `part` facts describe first, second, and third postings | A fractional first label provides no additional information; zero-based labels are possible but were not selected. |
| Effective default instalment count 1; `Event.Installments == 0` normalizes to 1 | Go's zero-valued field represents omission; explicit zero is indistinguishable from omission. Negative counts are rejected, and the splitting helper requires a positive count | Half a posting has no operational meaning. A fractional count cannot inhabit the Go integer field. |
| Remainder increment 1 minor unit | Integer division yields the conserved quotient and remainder; the first `remainder` pieces receive exactly one extra unit | Adding half a unit violates currency precision. Adding more than one makes pieces less equal than necessary. |
| One full settlement ends one hold | Simplifies capture lifecycle and releases all unused reserved funds | Half the hold cannot describe general residual captures without additional lifecycle commands and balances. The actual difference between AED 200.00 and 185.00 is AED 15.00. |
| At most one full reversal of a posted credit/debit | Prevents duplicate compensation; its amount is the negative sum of target postings | Half a reversal would require a partial-reversal allocation and remaining-principal policy, neither of which is implemented. |
| One capitalization record per account at finish | A single credit per account realizes that account's exact sum of daily accruals | Half a record is impossible; multiple credits would depart from the required single credit. Zero capitalization is still recorded for a zero-accrual account. |
| No automatic expiry duration | The request gives no hold timeout; explicit `EXPIRE` is supported | There is no duration to halve. Picking any timeout, including three or six days, would invent an external lifecycle policy. |
| No separate business maximum balance, instalment count, or journal length | Stored monetary values have the checked `int64` representation limit; collection sizes have no application-level resource cap | There is no separate resource limit to halve. This is a deliberate resource-control omission, discussed in the architecture draft. |
| Format negative magnitude using `-(amount+1)` then add unsigned 1 | Formats even `math.MinInt64` without negating an unrepresentable positive signed magnitude | The one-unit offset avoids the single signed-boundary overflow and is restored exactly. Half an integer unit is unavailable; a larger offset is unnecessary. |
| Go 1.22 language/module target; zero external dependencies | An explicit modern Go baseline keeps the core and `testing` suite portable with the standard library. Local verification used Go 1.26.5 | A version number is an API compatibility label, not a quantity to halve. Halving zero dependencies still means zero. |

## Derived results, not tuning constants

E10's `(3334, 3333, 3333)` BHD minor-unit split follows from `divmod(10000, 3) = (3333, 1)`. Fees of 2,500 minor units are assessed for Days 2, 4, and 5, totaling 7,500 AED minor units. Final pre-capitalization AED closes are `(25000, 22500, 62500, 41500, 39000, 39000)`; rounded daily accruals are `(10, 9, 25, 17, 16, 16)`, totaling 93 minor units. The final AED ledger is 39,093 minor units, or AED 390.93. BHD Day 5 and Day 6 accrue four minor units each, totaling eight; its final ledger is 10,008 minor units, or BHD 10.008. Halving a derived result would break the underlying calculation, not change a selected parameter.

## Test fixtures and boundary probes

Tests use the supplied amounts wherever possible. Additional literal amounts are synthetic probes, not business constants. `1.005` and `1.015` AED and `1.0005` and `1.0015` BHD straddle ties whose retained final digit is respectively even or odd; `-1.015` checks symmetric negative rounding. Their expected stored values are 100, 102, 1,000, 1,002, and -102 minor units. Halving these inputs would remove the intended midpoint cases.

The Go parser rejects `NaN`, `Infinity`, invalid string `bad`, exponent `1e3`, and fraction `1/2`. Their exact spellings exercise distinct prohibited input classes, rather than economic parameters. Boundary strings `92233720368547758.07` and `-92233720368547758.08` AED represent exactly `math.MaxInt64` and `math.MinInt64` minor units and must parse and format without loss. `92233720368547758.08` and `-92233720368547758.09` are one minor unit beyond the corresponding boundary and must fail. Halving them would move them within range and remove the overflow check. Expected monetary literals elsewhere in the acceptance tests are computed consequences of the documented policies, not alternate policy values. The superseded Python large-integer probe tested 100 trailing decimal zeros; arbitrary-size stored money is no longer the Go design.

The remaining synthetic quantities are grouped below. For arbitrary readable fixtures, halving can remain a valid probe; that does not make the fixture a financial parameter.

| Synthetic fixture | Why selected, and effect of halving |
| --- | --- |
| Split sweep totals 0 through 14 (`total < 15`), counts 1 through 7 (`count < 8`) | A small exhaustive grid covers zero, more parts than units, exact divisions, and many remainders. Fifteen and eight are exclusive loop bounds. Halving the grid would also test conservation, with fewer combinations and smaller multi-part cases. |
| Invalid split total -1 and helper counts 0 and -1, alongside valid count 3 and unit total 1 | Minus one is the nearest invalid signed total/count; zero is the helper's invalid count boundary. Halving would turn the integer probes into fractional values that cannot inhabit these fields. Three is reused from the supplied instalment count. |
| AED 100.00 synthetic funding | Covers funded Auth-B's AED 90.00 hold and common lifecycle probes with round, readable amounts. Halving to AED 50.00 would cause the 90.00 and 60.00 approval probes to decline. It is also used in the intentionally failing stale-hold test. |
| AED holds 60.00 plus 40.00 | Sum exactly to the 100.00 funding to check zero remaining available balance and aggregation of two holds. Halving both would leave 50.00 free and remove the zero-boundary check. |
| AED 0.01 extra hold and tiny tail credits | One AED minor unit checks a decline immediately beyond zero availability and exercises repeated reassessment without materially funding the account. Half, AED 0.005, rounds to zero under ties to even and changes command validation. Three tail credits ensure more than one repeated evaluation; half of three is not an integer repeat count. |
| AED hold/capture amounts 50.00 and 40.00 | Readable lifecycle variants check unused hold release, duplicate settlement, and account-scoped identifiers. Half can also exercise those state transitions, but would change expected cash and hold quantities. |
| AED 100.01 declined hold | The nearest representable amount above 100.00 funding isolates the inclusive authorization floor. Half would approve and fail to exercise decline behavior. |
| AED 60.01 oversettlement | One minor unit above the 60.00 hold checks the inclusive settlement ceiling. Half would fit and would no longer test rejection. |
| AED 150.00 ordinary debit | Exceeds 100.00 funding before a known 50.00 settlement, isolating acceptance of an already-authorized settlement after cash becomes overdrawn. Half, 75.00, would leave cash positive before settlement. |
| BHD 1.000 funding/debit, 0.500 hold, and 0.001 corrective credit | Readable three-decimal fixtures check account isolation, a half-funded hold, and missing fee policy on a nearly fully negative BHD balance. The smallest credit cannot be halved while remaining representable. Halving the larger amounts changes expected balances but can still expose the policy/type separation; none establishes a BHD fee. |
| AED 1.00, -1.00, 0.004, and 10.00 in validation probes | One whole unit gives readable positive/negative magnitudes, 0.004 is a positive amount below half a fils that rounds to zero, and 10.00 is arbitrary money on a deliberately date-invalid command. Halving the whole-unit amounts or 0.004 would often preserve the intended rejection, which is why these are fixtures rather than economic constants. |
| Mutation attempts 99,999 minor units and string 999.00 | Obvious alternate values check that caller-owned Event values, account slices, and returned record snapshots cannot corrupt internal state. Halving would also expose aliasing, but these readable changes make failures easy to distinguish from the 100.00 funding. |
| Cash overflow openings `math.MaxInt64` / `math.MinInt64` and AED 0.01 attempts | One minor unit beyond the signed limits is the smallest possible balance overflow. A late credit uses booking Day 2/value Day 1 against a Day 2 maximum balance to check every affected day, not only its own value date. Halving the openings would leave headroom; halving the increment would round to zero. |
| Capitalization-overflow accounts opening at 10,000 minor units and `math.MaxInt64` | The first reuses readable AED 100.00 funding as a control that must not receive a partial capitalization when the second cannot accept interest. A Day 6 debit of the entire maximum balance creates room for a successful retry. Halving the maximum opening would prevent the failure; halving the control funding would remain a valid smaller control with different accruals. |
| Supplemental leading-zero parser probes `010` and `0009` | Ten makes an octal interpretation visibly wrong, and nine is outside the octal digit set. Both must parse as ordinary decimal amounts. Halving their numeric values would remove those specific distinctions. |
| Invalid configured fee -1 minor unit | Nearest invalid fee configuration; zero is allowed to represent missing policy. Half is not an integer minor unit. |
| Invalid day 0, out-of-window day 7, and future value day 2 with booking day 1 | Nearest window/order violations. Halving can move a day into range or make it noninteger, changing what rejection is exercised. The malformed-clock regression uses booked Day 6 / value Day 7 against a Day 1 overdrawn account so that unintended clock advancement would be financially observable. |
| Derived counts 12 closes and one or two receipt/posting assertions | Twelve is two accounts times six days. Single/duplicate posting counts follow the action being verified; changing or halving them would permit omissions or duplicate cash. Event-prefix lengths and indexes follow the supplied event positions, rather than tunable numerical constants. |

The opt-in failing test funds 100.00 AED, creates a 60.00 AED hold, then closes the six-day window without a release event. These amounts isolate the missing automatic-expiry policy from E8's actual insufficient-funds decline. The assertion's target state is deliberately unmet; no six-day timeout has been installed merely because six days have elapsed.
